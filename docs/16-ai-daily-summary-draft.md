# #16 AI 每日总结——设计稿 (v1)

> 状态: **已落地（2026-09-10），未走对抗审稿轮**。本文是落地后回填的设计说明，不是 v1 那种"先评审再动手"的终稿——
> 本轮由谷雨直接拍板四条（见 §1），实现以测试为准：`tests/bindtest.js` 的【D15】84 条断言覆盖本文全部行为。
> 决策记录见 `00-decisions.md` D15；对外契约见 `data-contract.md` v1.5。
> 来源: 谷雨 2026-09-10 需求「给这个项目加一个 AI 功能，每天晚上 12 点到当天的笔记总结」。

## 0. 一句话

跨过「一天的边界」（默认凌晨 4 点，跟随 `dayStartHour`）时，把**刚结束那一天**的微信记录交给用户
自己配置的 OpenAI 兼容接口，总结写进当天笔记末尾的 `## AI 总结` 一节；到点（默认 08:00）再推一次微信。
默认关闭，零 key 时记录链路一个字节都不变。

## 1. 需求与四条拍板

谷雨的原话是「每天晚上 12 点到当天的笔记总结」。落到这个插件里有四个歧义点，逐条问过：

| 歧义 | 拍板 | 理由 |
|---|---|---|
| 00:00 还是逻辑日边界？ | **延迟到「一天的边界」** | 00:00 时逻辑日还没结束（契约 v1.2：凌晨 4 点前算前一天），零点总结会漏掉 00:00–04:00 熬夜写的部分。她选宁可晚生成也要完整 |
| 总结写到哪？ | **两个都要**：写进笔记的 `## AI 总结` 一节 + 推微信 | 落库能长期回看，推送能在手机上直接读 |
| 素材取多少？ | **只取微信随手记记下的内容** | 共用每日笔记模式下，用户自己在同一个文件里写的东西不外发给第三方接口 |
| 什么时候推微信？ | **生成在边界，推送挪到早上**（默认 08:00） | 边界是凌晨 4 点；凌晨 4 点震手机是事故，不是功能 |

默认关、且必须用户自己填 Key：D2 记下的代价（「零 key 也完整可用」要重新表述）就在这里兑现——
不打开开关就一个字节都不出本机。

## 2. 时机：为什么总结的是「昨天」

三个纯函数把时间语义钉死，全部表驱动可测：

- `logicalTimeReached(timeStr, now)` —— 逻辑日时钟。把「几点几分」落到以 `dayStartHour` 为 0 点的
  一天里：`nowLogical = (nowMin - dayStart + 1440) % 1440 >= wantLogical`。
  从 `reminderDue` 里抽出来的（原来只有每日提醒用），现在提醒与总结推送共用一条——
  同一套时间语义写两遍必然漂移。
  **注意它的两个性质**：边界前（比如 03:59）当天的 08:00 已经算"到点"；一到 04:00 就归零。
  所以 04:00 生成的总结不会立刻推，正好等到 08:00。
- `logicalDayFlipped(now)` —— `logicalTodayStr(now) === todayStr(now)`。
  成立 ⟺ 已跨过 `dayStartHour` 边界 ⟺ 刚结束那一天已经攒齐。`dayStartHour = 0` 时恒真（契约允许零点切天）。
- `summaryDue(ctx)` —— 开关开 + AI 配好 + 边界已过 + 这天没处理过 + 没超重试上限。

于是 `_summaryGenerateTick` 里的目标日就是 `yesterdayStr(now)`：边界之后的任何时刻，
「刚结束的逻辑日」= 日历上的昨天。**边界之前绝不能跑**——02:00 时 `yesterdayStr` 恰好等于
当天逻辑日，总结会把写了一半的一天封掉，`logicalDayFlipped` 就是拦这个的。

只总结刚结束的那一天，不回头补陈年旧账：`summary_last_date` 一旦更晚就不再倒退
（`summaryDue` 里 `prevDay <= lastDate` 直接拒）。

## 3. 状态机与字段

全部状态在 `data.session`（`data.json`，不在 vault 可见区域，符合 D5）：

| 字段 | 作用 |
|---|---|
| `summary_last_date` | 已处理过的逻辑日。成功 / 放弃 / 没素材**都记**，一天只做一次 |
| `summary_attempts` + `summary_attempt_day` | 生成重试计数**必须成对**：换天之后计数要归零，否则昨天的失败次数会误伤新的一天 |
| `summary_push_day` | 已写好、等待推送的日子 |
| `summary_push_attempts` | 推送重试计数 |
| `summary_pending_delivery` | 主动推送放弃后，留给「下次对话带出」的日子 |
| `summary_last_result` | 最近一次结果（诊断用）。主动推送到底发不发得出去，019 时代没人知道，现在按返回码见分晓 |

两个阶段，搭每日提醒那班 60s 的 tick（`_summaryTick` 自带 `_summaryBusy` 重入闸：一次总结最长可能跑 90s，
不能让下一分钟的 tick 再起一个并发调用）：

```
tick
 ├─ 开关关?  → 清掉待推与待带出的, 保留 summary_last_date(再打开时不补陈年旧账), 返回
 ├─ AI 没配好? → 返回
 ├─ 阶段一 _summaryGenerateTick(now)   不需要管道: 纯本地读文件 + 一次接口调用
 │    ├─ 逻辑日没翻篇 → 返回
 │    ├─ summaryDue 不成立 → 返回
 │    ├─ 先记账(attempts+1) 并 persist —— 断在这中间也只是白试一次, 不会下次打开从零开始
 │    ├─ summarizeDay(prevDay) = 读素材 → AI → 写回笔记
 │    └─ 成功: last_date=prevDay, push_day=prevDay;  失败: 记 error, 满 3 次放弃
 └─ 阶段二 _summaryPushTick(now)      需要管道活着 + 已绑定 + 未被 -14 冷却
      ├─ summaryPushDue 不成立(没到点/满 3 次) → 返回
      ├─ readSummary(day) 从笔记读回正文(推的和笔记里看到的必然一致, 不另存一份文本)
      ├─ 先记账再发("发成功但响应丢了"不能变成双发, 与每日提醒同款)
      └─ 失败满 3 次 → push_day 清掉, 转 summary_pending_delivery
```

**失败降级**是这里唯一"聪明"的地方：D3 早就确认微信主动发消息依赖用户入站产生的 `context_token`，
越规律越可能发不出去。所以连推 3 次失败后不再重试，改成 `summary_pending_delivery`——
用户下次跟 bot 说话时，`DiaryAgent.onMessage` 调 `_takePendingSummaryDelivery()` 把总结附在回复里带出去。
用户开口恰好刷新了窗口，这是最可靠的送达时机。取一次就清，只带一次。

## 4. 落位：为什么总结节必须在文件末尾

这是整件事风险最高的地方：记录区的写入路径（追加 / 撤回 / 封存 / 段数）是字节级保真的，
而总结是**模型生成的、写在同一个文件里的**内容。放错位置就会静默破坏契约。

**候选方案与取舍**：

- ❌ **文件开头（标题之后）**：所有"追到文件末尾"的操作天然安全，但 `sealContent` 与
  `countMessages` 是全文扫描，会把总结算进段数；模型编出的 `**09:30**` 还会顶掉
  `content.search(HEADER_RE_G)`（外来文件分支靠它找记录区起点）。
- ❌ **单独一个文件**：最干净，但谷雨明确要"写进当天笔记的 `## AI 总结` 一节"。
- ✅ **文件末尾 + 入口 split / 出口 join**：记录区实现根本不需要知道总结节存在。

```
content = [ 记录区 rec ][ 总结节 summary ]
splitSummarySection(content, heading) → { rec, summary }    // 没有总结节时 rec === content 逐字节
joinSummarySection(rec, summary)     → rec + summary        // summary 为空时原样返回 rec
```

拆开再拼回是**逐字节相同**的（`bindtest` D15.5 盯着），因为没有总结节的文件走的是恒等路径。
`join` 里那点归一化只在 `rec` 已经被改过时生效，且只动交界处的空行——保证 `##` 标题永远另起一段
（贴在上一条记录后面会被 CommonMark 当成正文，节就废了）。

**四个触点**（独立模式；共用模式下总结节在记录节之外，这四处天然是 no-op）：

| 触点 | 改动 |
|---|---|
| `_appendRaw` | 新块追在 `sp.rec` 末尾，再 join 回去 → 记录永远插在总结之前 |
| `undoLastBlock` | `removeLastBlock(sp.rec)`，总结节原样接回 → 撤回撤的是记录，不是 AI 的总结 |
| `finalizeDay` | `sealContent(sp.rec)` → 封存行落在总结节之前，总结仍在文件最后 |
| `_count` | 数段前先 `splitSummarySection` → AI 写的要点不算"今天第 N 段"；`countDay` 走它，一处改完 |

**模型输出的消毒**（`sanitizeSummaryOutput`）是第二道闸，两道都必要：

- 形如 `**09:30**` 的整行 → `escapeSummaryHeaderLines` 转义成 `\*\*09:30\*\*`。
  不转义的话 `HEADER_RE_G` 会把它当成段头：段数虚报、同分钟合并判断错乱、外来文件分支找错记录区起点。
- `#`×1–6 + 空格开头的行 → `escapeHeadingLines`（复用 v1.4 已有的）。不转义的话它会成为
  总结节的终点，下次重算就把尾巴留在外面了。
- ``` 围栏行 → `escapeFenceLines`（同上）。
- 去代码围栏、去模型自加的「# 今日总结」标题行与「以下是总结:」开场白、剥整段外层引号。
- 空输出 → `""`，`AiClient.summarize` 当成失败抛出，**绝不落盘**（不静默降级成"把原文当总结"）。

**覆盖式而非追加式**：总结是可再生的派生内容，同一天重算必须替换。它是本插件唯一不适用
「只追加、历史段落永不改写」的写入，因此独占文件末尾、与记录区物理隔离，并在 README 与
`data-contract.md` v1.5 里都写明。

## 5. 素材范围：用户自己写的不外发

`summarySourceRegion(content, opts)` 圈出"只属于微信随手记"的那段：

| 模式 | 取什么 |
|---|---|
| 共用（`sharedDailyNote`） | `## <sectionHeading>` 一节正文；**用户在同一文件里写的别的内容一个字都不进** |
| 独立 | 去掉 frontmatter 与日期标题后的全部内容 |
| 独立 + 外来文件（B1） | 只取第一个 `**HH:MM**` 段头之后；段头之前是用户自己的东西 |

**读素材前先 `splitSummarySection` 摘掉已有的总结节**——否则第二次总结会把上一次的总结当成
"用户原话"喂回去，形成自我循环（D15.6 有断言）。

`cleanSummarySource` 再做一次清洗：段头、标题行、封存行（含封存线的 `---` 分隔）、纯附件嵌入行全部去掉，
语音的 `🎤 ` 标记**留着**（它是"说的"不是"写的"，总结时值得区分）。真消息不会被误伤：
契约已把行首 `# `/`---`/`_(` 转义过。产出 `{ text, blocks, chars, truncated }`，
`blocks === 0` 就不调用 AI、不落笔。素材上限 12000 字，超出截断并注明。

## 6. 提示词策略

`SUMMARY_PROMPT` 的目标是「替用户看了一眼今天」，不是文学创作。硬要求：保留具体人名/地名/数字/时间、
**只依据原话不编造**、不给建议清单、不写客套、不输出标题行与代码块。温度 0.4，超时 90s
（长文总结比润色慢；桌面端 `requestUrl` 没有应用层超时，必须自己兜）。

出处行（`> 由 <model> 生成 · <时间> · N 段素材 · 仅供参考`）刻意写进笔记：日后翻回来能一眼看出
这段是 AI 写的。

## 7. 设置项

| 字段 | 默认 | 说明 |
|---|---|---|
| `aiSummaryEnabled` | `false` | 默认关。三项没配全时打开也不会有任何请求，只 Notice 提示 |
| `aiSummaryHeading` | `AI 总结` | 写进笔记的二级节标题。**与记录节同名会被兜底换回默认值**（同名会当场毁掉记录区），设置页也拦 |
| `aiSummaryPushTime` | `08:00` | 微信推送时刻，形状校验复用 `REMINDER_TIME_RE`，语义走逻辑日时钟 |

复用 0.3.0 就留着的 `aiApiUrl` / `aiModel` / `getAiKey()`（Key 在 `SecretStorage`，不进 vault）。
设置页原来的「AI (暂未启用)」占位块换成真控件：配置三项 → 开关 → 节标题 → 推送时间 →
「立即总结昨天」按钮（手动跑一次，用来验证配置，也用来补跑昨天）。

## 9. 不做 / 待实测

- **不做**：周报月报；补跑陈年旧账；对话式追问（`ChatHandler` 仍按 D2 的结论挂在墙上）；
  多套提示词/多模型选择。
- **待实测**（需要真机 + 真 Key）：
  1. 真实模型的输出长度与格式稳定性——消毒层能兜住脏输出，但"质量"只能真跑才知道；
  2. 早上 08:00 的主动推送实际送达率（`summary_last_result` 就是为攒这个数据留的）——
     这同时也是 D3 那个"真实推送窗口"问题的又一组观测样本；
  3. 大库（一天几百段）时 12000 字截断是否够用。
- **未走审稿轮**：本仓库的大功能（#15）惯例是"设计稿 → 对抗审稿若干轮 → 落地 → diff 审查轮"。
  这一轮没有走，风险集中在 §4 的四个触点与消毒层；这两处恰好是测试覆盖最密的地方。
