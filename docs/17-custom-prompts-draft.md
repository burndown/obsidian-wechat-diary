# #17 自定义提示词——设计稿 (v1)

> 状态: **已落地（2026-09-10）**，未走对抗审稿轮。决策记录见 `00-decisions.md` D16；
> 对外契约见 `data-contract.md` v1.6。实现以测试为准：`tests/bindtest.js` 的【D16】78 条断言覆盖本文全部行为。
> 来源: 谷雨 2026-09-10 需求「给插件加一个自定义提示词功能，而不是只是总结」。

## 0. 一句话

除了内置的「总结」，用户还能定义若干条提示词。一条 = **触发词** + **提示词** + **写进笔记的节标题**。
在微信里发那个触发词，就把**今天到现在**的微信记录交给 AI、按这条提示词产出，回给用户并写进它自己那一节。

## 1. 形态（三问定案）

| 问题 | 定案 | 理由 |
|---|---|---|
| 自定义的粒度 | **多条**，不是单个可编辑文本框 | 单条同一时间只能有一种产物，想要第二件事就得把第一件改掉 |
| 产物落到哪 | **每条写自己的节** | 几件事的产物可以同时留在笔记里、互不覆盖；节扫描本来就按标题认节 |
| 内置「总结」 | **保留，可用不可删不可改** | 它是「每日定时总结」那条路的固定出口，动了会让定时行为跟着漂 |

设置项 `aiPrompts`（默认 `[]`）= `[{ keyword, prompt, heading }]`。

## 2. 触发：内置命令永远优先

触发词匹配与内置命令共用同一套归一化（`intentForms`），所以「待办！」「待办吧」「“待办”」都能命中。

**顺序**：`_dispatch` 先跑 `detectIntent`，只有它判定为"内容"（`INTENT.DIARY`）时，才去问
`matchCustomPrompt`。

```
detectIntent(text)  ──命中内置命令──▶ 内置命令照旧（撤回/晚安/在吗/帮助/总结…）
        │
        └─判为"内容"─▶ matchCustomPrompt(text, settings.aiPrompts) ──命中──▶ INTENT.CUSTOM
```

这道顺序是**纵深防御**：用户手改 `data.json` 塞一个触发词「撤回」，撤回功能照样工作
（D16.9 有用例）。保存时另有一道拦截把内置词直接拒掉，并说明原因——不然用户会以为"我设了却没反应"。

**长度闸门**：`matchCustomPrompt` 用精确匹配（`norm === keyword || forms.includes(keyword)`），
所以「今天开完会写了个待办」这种长句天然不会命中，与内置命令的 `MAX_COMMAND_LEN` 口径一致。

## 3. 校验（保存前，都是数据安全）

**触发词** `validatePromptKeyword(raw, existing, self)`：
- 空 / 换行 / 超 `MAX_COMMAND_LEN`（15）个字 → 拒
- 归一化后撞内置命令词全集（`reservedCommandWords()`）/ 撞 `记：` 前缀 → 拒
- 撞别的条目 → 拒；与自己相同 → 放行（改其它字段时不误伤）
- 通过则返回**归一化后**的值（`  待办吧  ` → `待办`；`TODO` → `todo`）

**节标题** `validatePromptHeading(raw, opts)`：
- 复用 `normalizeHeading`（非空 / 无换行 / ≤30 码点 / 剥前导 `#`）
- 撞记录节标题、内置总结节标题、别的自定义节标题 → 拒

节标题撞车不是体验问题：`locateSection` 靠标题定位，重名会让它认不出谁是谁，记录区当场就乱了。
所以设置页拦一道，`_summaryHeading()` 那种运行时兜底再来一道。

## 4. 执行：与「总结」共用整条流水线

`_runCustomPrompt(entry)` 与 `_onDemandSummary()` 是同胞：

| 环节 | 共用 |
|---|---|
| 素材范围 | `writer.readSummarySource(day)` —— 今天到现在、只取微信随手记的内容、先摘掉全部 AI 派生节 |
| 提示词渲染 | `renderPromptTemplate(tpl, {day, weekday, entries})` |
| 调用与消毒 | `ai.runPrompt(...)` → `sanitizeSummaryOutput`（转义段头行/标题行，超长截断） |
| 落盘 | `writer.writeSummary(day, text, meta, heading)` —— 覆盖式，各写各的节 |
| 防手抖 | 10 分钟内 + 素材段数没变 → 复用笔记里那份，不再烧 token |
| 失败 | 不落笔；`aiErrorText(kind)` 说原因，回执用该条自己的名字 |

**逐条独立的防手抖**：状态记在 `session.prompts[<节标题>]` 上（不是全局一个），
所以跑「待办」不会让「周报」被误判成"刚算过"。条目被删/改名后的残键由 `_prunePromptState()` 清掉，
不让它跟着 `data.json` 无限长。

**自定义提示词不写 `summary_last_date`**：那是「每日定时总结」那条路的账，碰了它当天边界的定时总结
会误判成"已处理过"而跳过——与「总结」命令同一条纪律。

## 5. 提示词模板：不写 `{entries}` 也要把记录接上去

```
{day} {weekday} {entries}   —— 全部可选
```

**没写 `{entries}` 时把素材接在提示词末尾**。不这么做的话用户会写出一个"模型根本看不到记录"的提示词，
而且**失败得不响**：模型照样给出一个像模像样的回答，用户以为在做总结，其实它在凭空编。
这类静默失真比报错危险得多，所以宁可在渲染层兜住。设置页的说明也写了这一条。

## 6. 这轮修掉的真实缺陷：记录区切分写死在单个标题上

D15 的实现里，"记录区"是这样切的：

```js
const rec = splitSummarySection(text, this._summaryHeading()).rec;   // D15: 只认内置总结节
```

只要**派生节只有一个**（内置总结）这是对的。D16 让派生节变成 N 个，而**自定义节可能先于内置总结节
被创建**（用户先发了自定义触发词、还没跑过总结），文件顺序就成了 `[记录][AI 待办][AI 总结]`。
此时上面那行把 `[记录][AI 待办]` 整段当成记录区，后果是三重的：

1. **段数虚报**：AI 产物里的块被数成"今天第 N 段"。
2. **新记录被写进 AI 节里**：`_appendRaw` 把新块追到"记录区"末尾，也就是 AI 节后面。
3. **撤回会删掉 AI 产物**：`removeLastBlock` 从末尾找消息块，找到的是 AI 写的东西。

改法是把"一个标题"换成"一组标题里最早出现的那个"：

```js
// 记录区 = 最早出现的那个 AI 派生节之前的一切
function splitRecordRegion(content, headings) {   // headings = writer._aiHeadings()
  ...取各标题 locateSection 的 headingStart 最小值...
  return { rec, tail };                            // tail = 全部派生节，顺序原样
}
```

`_count` / `_appendRaw` / `undoLastBlock` / `finalizeDay` 四处统一改用它，`joinSummarySection(rec, tail)`
把 tail 原样接回。没有派生节时 `rec` 逐字节等于原文、`tail` 为空，join 原样返回——**没有 AI 节的文件
行为一字不变**（D15.5/D15.6 那些字节保真断言继续盯着）。

> 这条不是设计时想到的，是 §D16.10 那组回归用例抓出来的。同类教训在 #15 的审稿轮里也出现过：
> 写入路径上"只认一个标题"的假设，一旦标题变成用户可配就必然出事。

## 7. 已知约束：AI 节之间 / 最后一个 AI 节之后的内容会被覆盖

按 Markdown 的节边界规则（`locateSection`），一个节的身体一直到"下一个任意级别标题"；
最后一个节的 bodyEnd = 文件末尾。而派生节固定排在文件末尾，于是：

- 写在两个 AI 节**之间**的内容 → 属于前一个 AI 节
- 写在**最后一个 AI 节之后**的内容 → 属于最后一个 AI 节

两者都会在下次重算时被整节覆盖。README 的「限制」与契约 v1.6 都写明了这一条。

**要根治**得给每个 AI 节加一个结束标记（如 `<!-- /wechat-diary-ai -->`），让覆盖与素材摘除都只到标记
为止——那样标记之后的内容才真正属于用户。代价是写入格式变更（老文件没有标记，得按"到下一个标题"
的旧规则兼容），所以本轮没做，留作后续决定。

## 8. 测试

`tests/bindtest.js`【D16】78 条，分十组：触发词匹配与归一化 / 提示词模板（含不写 `{entries}` 的兜底）/
多节摘除 / 触发词校验（内置词、重复、长度、归一化）/ 节标题校验（撞记录节、撞内置节、撞彼此）/
真 `DiaryWriter` 的各节共存与覆盖 / 全链路（**真跑一次 `runPrompt`，抓发出去的 prompt 断言用户提示词
与记录都在**）/ 与内置「总结」并存 + 逐条防手抖 / 各处前置失败与"内置优先"纵深防御 /
**自定义节先落地的回归组**（段数、追加位置、撤回、封存、素材五路都验）。

## 9. 不做

- 按条目配置模型 / 温度 / 超时（现在是全局一套）
- 条目拖拽排序（列表顺序不影响行为，节标题才是身份）
- 条目级"跑哪一天"参数——`总结昨天`/`总结上周` 那类日期解析仍是整套悬着的歧义（见 §9 上一版）
- 给 AI 节加结束标记（见 §7，属格式变更，留给后续决定）
